## 3) Wiring (all native C++, `Player/CombatForgeCharacter.*`)

- `FirstPersonArms` now lives under **`ViewModelRoot`** (was: FirstPersonCamera). That
  buys, with zero extra code: ADS/recoil/reload/feel sway (ViewModelRoot offsets), build-
  mode hide, elimination hide, respawn re-show (all `SetVisibility(..., propagate)` on
  ViewModelRoot), and the EnforceSingleFirstPersonWeapon exemption (already matched both
  the component pointer and anything attached to ViewModelRoot).
- Ctor assigns `FirstPersonArmsMesh` + new `FirstPersonArmsAnim` via ConstructorHelpers;
  `ApplyArtLoadout` mounts the mesh ONLY when both are present (an unanimated arms mesh
  is a T-pose through the face) and plays the anim single-node looping.
- **`ComputeFPGunHandAnchors()`** returns the TWO points on the current gun the hands belong
  on, in ViewModelRoot space: the trigger grip and the handguard. Both come from
  `PFWeapon::ComputeAutoTPGrip`'s bounds recipe — its along-fraction is signed, so +0.55/0.55
  is the rear-low trigger grip (exactly what the TP palm-aim harvests) and -0.35/0.35 is the
  forward handguard. FP and TP therefore read identical per-weapon geometry.
- **`UpdateFirstPersonArmsPose()`** (re-run after every FP pose apply in `ApplyWeaponLoadout`
  + on mount): evaluate the hold anim now (`TickAnimation(0)` + `RefreshBoneTransforms`),
  read `hand_r`/`hand_l` in component space, then solve the **similarity transform that puts
  BOTH hands on the gun** — coarse-orient yaw -90 (mesh +Y-forward → viewmodel +X),
  `FQuat::FindBetweenNormals` rotates the anim's hand line onto the gun's grip→handguard
  line, uniform scale = length ratio (clamped 0.85–1.15; arm length is a character trait, not
  a weapon trait), translate so hand_r lands on the grip. hand_l then lands on the handguard
  by construction. This is the proven TP recipe ("derive the pose from the ANIMATION") run in
  reverse — the hands follow the gun.
  - v1 aligned only the hand-pair DIRECTION and seated the right hand; Tom's first look:
    *"it's not mounted to the gun. At least the left hand is not."* A rifle hold is two point
    constraints, hence the two-anchor solve.
- Per-weapon by construction: reads whatever FPLoc/FPRot/FPScale won (catalog hand-tuned
  true-scale row / ComputeTrueScaleFP derivation / session pf.WeaponFP cache).

## 4b) Verification hook (dev builds only)

`pf.FPArmsVerify 1` (launch `... /Game/Maps/L_Graybox -game -ExecCmds="pf.FPArmsVerify 1"`)
runs a 1s-tick state machine: dismiss the boot loading menu once warmup completes (its
`OnEnterClicked` UFUNCTION, invoked reflectively so this dev harness doesn't widen the
widget's API) → equip the **lmg_01** reference → log `FPArmsVerify:` lines + save screenshot
`FPArmsVerify.png` → quit. Hard-capped at 90 ticks so it always terminates.

Logged numbers: per-hand anchor error (`handR->grip`, `handL->foregrip`; each should be
within a palm-width, ~5uu), the solved `armsScale`, and per-bone forward-of-camera distance
vs the 4uu near plane.

NOTE for the next run: launch it from **PowerShell, not Git Bash** — bash rewrites the bare
`/Game/Maps/L_Graybox` argument into `C:/Program Files/Git/Game/...` and the engine then
reports "the map specified in the command line could not be found."

  wrong up close; a pistol-pose clip would need its own retarget pass.
- **"Pretty darn close," not perfect** (Tom, after the two-anchor solve). Residual comes from
  three places, in likely order of contribution: (a) the handguard anchor is a bounds
  fraction (-0.35 along, 0.35 down), not the mesh's real handguard — a per-weapon foregrip
  offset in FPFWeaponDef would nail it; (b) the 0.85–1.15 arms-scale clamp, which pushes any
  overflow into the support hand; (c) palm-centre vs bone-pivot (hand_r/hand_l are wrist
  bones, so the visual palm sits ~2-3uu past the anchor). Run `pf.FPArmsVerify` first — the
  logged per-hand error says which one is actually biting before anything gets tuned.
- **Arms don't hold the build tool** — build mode simply hides gun+arms (inherited
  behavior, consistent with before).
